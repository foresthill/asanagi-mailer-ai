# 09 — オンプレAI（社内Ollama）と接続の安定化

朝凪のAIを **社外クラウドでなく社内の Ollama** に向ける。メール本文・宛先が
社内LANから出ないため [local-first](00-overview.md) / [PIIマスキング](06-pii-masking.md)
思想と完全に一致する。プロバイダ抽象（`resolveModel()` / `EmailProvider`）の継ぎ目で
吸収しているので、機能コードは一切変えずに向け先だけ差し替わる。

## 原則

- AIの向け先はアプリ内設定（`.data`）で切替。キー・エンドポイントは端末内のみ。
- **落ちても黙ってクラウドへ流さない**（PII漏れガード）。オンプレが不通なら
  「ローカルの簡易判定」か「明示エラー」に倒す。クラウドへのフォールバックは
  既定で**しない**（§3）。
- 「社内Ollamaに向ける」は **OpenAI互換 `/v1`** を使う。Ollama は `/v1/chat/completions`
  ・`/v1/models` を持つので、`createOpenAI({ baseURL })` でそのまま話せる。

## 1. 向け先の設定（実装済・無改修で成立）

- `src/lib/ai/model.ts`：`openai` プロバイダ選択時のみ `baseUrl` を
  `createOpenAI({ apiKey: key||"ollama", baseURL })` に渡す。素のローカル Ollama は
  鍵不要（`baseUrl` があれば `configured` 扱い）、トークンgatingなreverse proxyなら
  `keys.openai` が Bearer として送られる。
- 接続設定UI（`src/components/mail/ConnectionsSettings.tsx`）に
  「エンドポイントURL（OpenAI互換）」欄。**URLを丸ごと受ける**ので、既定の
  `11434` でも、ポートを逃がした `11435` でも、そのまま書けば吸収する
  （placeholder で `http://localhost:11434/v1（Ollama）` を案内）。

## 2. モデル自動取得・接続確認（実装済）

手打ちのモデルID（サーバに無い名前）は 404 になる。これを防ぐため：

- `POST /api/settings/ai/models`：保存前の `{ baseUrl, apiKey? }`（空なら保存値）で
  `{baseUrl}/models` を叩き、モデルID一覧を返す。8秒タイムアウトで**死んだトンネルは
  即座に失敗**（ダイアログを固めない）。OpenProject の `projects` ルートと同じ
  「接続して取得」パターン。
- UI：エンドポイント欄の下に **「モデル取得・接続確認」ボタン → 一覧をプルダウン化**。
  選ぶと `model` に入る。空欄時のみ先頭を既定提案（**ユーザーが打った値は黙って
  上書きしない**）。
- これは **③の接続確認を兼ねる**：成功＝「✅接続OK（N件）」、失敗＝
  「⚠️ 未接続。SSHトンネル等を確認」。落ちている事実が設定画面で分かる。

## 3. PII漏れガード（既存挙動として成立）

オンプレが落ちた時にクラウドへ流れないことは、現行コードで既に満たしている：

- `classify` / `sweep`：失敗時フォールバックは **Jev → 「下のLLM」(＝設定中の
  provider。別プロバイダに替えない) → ヒューリスティック（ローカルkeyword・ネット無し）**。
- `ask` / `reply` / `review` 等の生成系：失敗時はそのままエラー返却（フォールバック無し）。

∴ Spark が不通でも anthropic 等クラウドへ本文を黙って送る経路は無い。
将来クラウドへのフォールバックを足す場合も、**既定OFF・明示オプトイン**を厳守する
（オンプレで守ったPIIを不通時に外へ出すのは本末転倒）。

## 4. トンネルの安定化（未実装・設計／要判断）

現状は手動 `ssh -N ... -L 11435:localhost:11434 spark-2` の窓を開きっぱなしにする運用。
**窓を閉じる＝11435が落ちる＝AI停止**で脆い。「窓を持たない常駐」に寄せたい。

### 事情（2026-11-06 実測）

- `spark-2` は鍵認証（`~/.ssh/igrek_ed25519`・公開IP `180.33.90.23:2223`）。無人起動の
  前提はあるが、**鍵のパスフレーズ無し or keychain/agent 登録**が必要（実装時に要検証）。
- **LAN↔WAN 問題**：社内NWからは公開IPが塞がることがあり、その時は LAN版
  `igrek-nvidia-spark-2`（192.168.1.217）で入る。外（テザリング等）では公開IP。
  → 単純な固定常駐だと「社内で繋がらない」事故が起きる。接続先の出し分けが要る。
- `11434` はこのMacのローカル Ollama が占有 → トンネルは **11435 に逃がす**のが実運用
  （`bind 11434: Address already in use` 回避）。

### 案A：autossh + macOS LaunchAgent（推奨・個人の常用向け）

- `autossh` が切断を検知して自動再接続、`launchd` の `KeepAlive` がプロセス自体を
  死なせない → **窓なし・回線瞬断も自己修復・再起動後も復活**。
- 前提：`brew install autossh`（DL要許可）、鍵の無人認証（上記）。
- **LAN→WANフォールバック**は autossh 単体では不可 → 小さなラッパースクリプトで
  「LAN(192.168.1.217)を先に試す→ダメなら公開IP(180.33.90.23:2223)」を選び、
  それを LaunchAgent から回す。
- ※ autossh/launchd の挙動は一般に確立しているが、**この端末での無人認証・
  LAN/WAN切替は実装時に実機検証する**（推測で「動く」と確定しない）。

### 案B：トークン認証の reverse proxy（SSHをやめる）

- Spark 側に OpenAI互換＋トークン認証の口を LAN/WAN に出す → SSH不要＝窓問題が消える。
  朝凪は `baseUrl` にその口、`keys.openai` にトークンを入れるだけ（§1で対応済み）。
- **非技術者（数人）展開の本命**：手動SSHトンネルは彼らには無理。トークンを欄に
  貼るだけなら運用できる。
- ただし **インフラ側の「穴」**（ポート公開・認証proxy）が未開通／可否未確認。
  セキュリティ設計（LAN限定 or 認証付き公開）をSEと詰める必要がある。

### 将来：デスクトップ版（Tauri）で朝凪自身がトンネルを常駐管理

- [v1デスクトップ化](DESKTOP.md) の文脈で、朝凪が ssh/autossh を **sidecar** として
  起動時に上げ・生存監視し、ヘッダに接続インジケータを出す。「自動で合わせる」の
  最終形。案A/Bの運用を内製化する位置づけ。
