# 設計書 10 — 学習の4層モデル（意識／個人的無意識／集合的無意識／超意識）

最終更新: 2026-11-09（個人的無意識＝返信文体の差分学習 A+B 実装後。集合的無意識は設計のみ）

## 0. これは何か

朝凪の「学習」を、nuko-ime（共同開発中のIME）と同じ**4層モデル**で整理する設計書。
どこまで実装済みで、どこが未着手か、そして**集合的無意識（チーム共有）をどう作るか**を定める。

> 出発点の問い（ユーザー）:
> 「AIの結果を出す → 人がどう修正したかを見る → 差分を取る → 学習する」が要る。
> さらに「個人的無意識で修正を入れ、今度はチームの集合知も共有できる機構があると良い。
> 集合的無意識は全人類？アプリ全員？」

---

## 1. 4層モデルと朝凪での実体

| 層 | nuko-ime 的意味 | 朝凪での実体 | 状態 |
|---|---|---|---|
| **意識** | 今まさに打っている文字 | 今の下書き・明示設定・手書きの文章作成メモ（`writing-note`） | ✅ |
| **個人的無意識** | その人の変換癖の蓄積 | その人の修正の蓄積（`.data`、端末内のみ） | 判定=✅ / 返信文体=✅（本書 §3） |
| **集合的無意識** | 共同体で共有される語彙・言い回し | **チーム／組織**で共有する抽象ルール（本文なし・opt-in） | ⬜ 設計のみ（§4） |
| **超意識** | 言語そのものの普遍構造 | **ベースLLM**（人類の言語知識を既に内包） | ✅ モデル側 |

### 「集合的無意識は全人類？アプリ全員？」への回答

local-first 原則（[00](00-overview.md) / [06](06-pii-masking.md)）から、設計上の結論はこうなる:

- **全人類 = 超意識 = ベースLLM**。既にモデルに入っているので、朝凪が集める必要はない。
- **集合的無意識 = チーム／組織**。全アプリユーザへの自動集約は「メール本文・PIIを端末外に出さない」
  原則と正面衝突するので**採らない**。共有するのは**本文ではなく、抽象化した文体ルール/判定傾向だけ**を
  **opt-in**で。
- 「アプリ全員の匿名集約」は、やるとしても差分プライバシ級の匿名化が要る**別案件**（§4.4）。今は範囲外。

## 2. 既に回っているループ：判定（重要度・仕分け）

[02](02-importance-triage-learning.md) の仕組みが、まさに「結果→修正→差分→学習」:

- AIが重要度を判定 → 一覧に理由つきで提示
- ユーザーが一凪レビュー/受信箱で修正（keep/archive/trash）
- `PATCH /api/judgments`・`POST /api/sweep/learn` が `recordImportanceFeedback` / `recordSweepAction` へ
- `signals.json` / `judgment-profile.json` / `sweep-actions.json` に蓄積 → 次回判定に反映
- 変遷は `.data` 内 git で版管理（`learning-history.ts`）。**本文は一切扱わない**

## 3. 個人的無意識：返信文体の差分学習（実装済み A+B）

判定にはあったループが、**返信の書き方**には無かった（`writing-note` は手書きのみ）。そこを塞いだ。

### (A) 素材を貯める — 決定論的・churnなし
- AIが生成した下書き（`data.ai` の自筆部分・引用なし）を控える（`ReplyComposer` の `aiBaselineRef`）
- 送信/予約成功時に、ユーザーが実際に送った自筆 head（`splitQuotedDraft` で引用除外）と対にして記録
- `recordWritingSample()` → `.data/writing-samples.json`（直近500件上限）
- **本文を含むためローカル専用**。学習履歴gitの TRACKED に載せない＝端末外に出ない
- `POST /api/ai/writing-samples`（空なら no-op）。送信体験をブロックしない fire-and-forget

### (B) 昇格 — on-demand pull・ユーザー承認
- 接続設定「最近の修正から学ぶ」で AI案 vs 自分の最終形を並べる（`WritingSamplesSection`）
- 「ルール化」→ `POST /api/ai/writing-rule` が差分から**一行ルールを提案**（例:「絵文字は使わない」）
- ユーザーが**編集して承認** →「メモに追加」で `writing-note` に**追記**（上書きしない）
- 済んだサンプルは一覧から外す（`DELETE /api/ai/writing-samples?at=`）

### 設計方針（ユーザー CLAUDE.md 準拠）
- **自動抽出・自動上書きしない**。「下書きを書くLLMと抽出するLLMが同じ＝利益相反」「自動生成＋
  高頻度 human review は破綻する」を避け、**提案だけLLM・保存はユーザー承認**（on-demand pull）
- 未設定/未接続でも**手書きで使える**（提案は空、テキストは編集可）＝両端に振り切る
- `writing-rule` の入力は他AIルートと同じく **PIIマスク**してから送る（関所）。返すルールは一般則

## 4. 集合的無意識：チーム共有（設計 — 未実装）

「個人の `writing-note` / 判定傾向を、チームでも共有したい」。これを **local-first を壊さずに** 作る。

### 4.1 共有してよいもの・ダメなもの

| 共有可（抽象ルール） | 共有不可（生データ） |
|---|---|
| 文体ルール行（例:「過剰敬語を避ける」「結論を先に書く」） | メール本文・下書き・`writing-samples`（生の差分） |
| 送信者ドメインの判定傾向（例:「@acme.co.jp は high 寄り」） | 個人宛先・個人名・社名そのもの（PII） |
| 定型の言い回し辞書（署名・挨拶のテンプレ） | OAuthトークン・APIキー（当然） |

原則: **素材（生の差分）は端末内のみ。共有するのは `writing-note` 相当の抽象ルールだけ**。
昇格(B)を通った＝ユーザーが一般則として承認した行だけが、チーム共有の候補になる。

### 4.2 共有の運び方（3案・小さく始める）

- **案A: 共有ファイル（最小）** — `team-rules.json` を共有ストレージ（Nextcloud [07](07-integrations.md) /
  社内共有）に置き、各端末が読み込んでマージ。書き戻しは opt-in。実装が最も軽い。
- **案B: 社内サーバ経由** — オンプレAI（[09](09-onprem-ai.md)）と同じ社内エンドポイントに
  `GET/POST /team/rules` を生やす。本文は出ない（ルール行のみ）。SSHトンネル/トークンの既存ゲートを再利用。
- **案C: devlog/OpenProject 等の既存連携に相乗り** — ルールを1リポ/1プロジェクトのドキュメントとして
  共有。履歴・レビューが付く代わりに重い。

> 推奨は **案A → 案B**。まず共有ファイルで「読み込みマージ＋opt-in書き戻し」を回し、
> 需要が出たら社内サーバ化する。中間の自動常駐同期は作らない（churn回避）。

### 4.3 マージの規律（上書き事故を防ぐ）

- チームルールは**個人ルールの下**に注入する（個人が最優先。チームは既定値）。プロンプト上は
  `writingNoteBlock` を「個人 > チーム」の順で合成。
- チーム側は**追記型**。個人の `writing-note` を機械が書き換えない。
- 取り込みは「プレビュー → ユーザーが採用行を選ぶ」on-demand pull。自動反映しない。

### 4.4 「アプリ全員」までやるか（保留）

全ユーザ匿名集約は、ルール行に固有名詞が混じる危険があり、差分プライバシ級の匿名化と
重い合意形成が要る。**今はやらない**。やるとしても「文体ルールの汎用辞書（固有名詞ゼロ保証）」に
限定し、別設計書で扱う。

## 5. 実装フェーズ（提案）

1. **Phase 1（済）**: 個人的無意識＝返信文体の差分学習 A+B（PR #346 / #347）
2. **Phase 2**: チーム共有・案A。`team-rules.json` の読み込みマージ＋プロンプト合成（個人 > チーム）。
   書き戻しは「このルールをチームに提案」ボタン（opt-in・プレビュー付き）
3. **Phase 3**: 需要次第で案B（社内サーバ `/team/rules`、本文なし、既存ゲート再利用）
4. **（保留）**: 全ユーザ匿名辞書は別案件

## 6. 不変条件（壊してはいけない）

- 生の差分・本文は**端末内のみ**（学習履歴gitにも載せない）
- 共有は**抽象ルールだけ・opt-in・プレビュー承認**。自動常駐同期/自動上書きはしない
- 個人ルール > チームルール（個人が最優先）
- オンプレが落ちても黙ってクラウドへ流さない（[09](09-onprem-ai.md) §3）
