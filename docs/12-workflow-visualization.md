# 設計書 12 — ワークフロー可視化（案件の俯瞰・誰待ち・関係者マップ）

最終更新: 2026-11-14（設計のみ・未実装。A/B/C の3ビューを段階導入する方針）

## 0. これは何か / 位置づけ

「いまメールで何の案件が動いていて、**誰待ち**で、**誰と誰が関わっている**か」を一目で掴むための
**可視化レイヤー**。[02](02-importance-triage-learning.md)（重要度・仕分け）と
[07](07-integrations.md)（連携）で既に朝凪が持っている/読み取っているデータを、
**新しい見せ方**にするだけのもので、**新しい情報源ではない**。

> 出発点の問い（ユーザー・2026-11-14）:
> 「プロジェクトの状況・誰のメールで止まっているか・関係者の構成図を、ワークフロー的に
> 可視化したい。原本は OpenProject 等にある前提で、メールのプロジェクト進行を読み取る
> 機能への追加というイメージ。これを朝凪に同梱するのはアリか？」
>
> 結論: **アリ**。朝凪が既に持つメール/案件データに素直に乗り、原本は OpenProject 等に
> 残したまま「俯瞰ビュー」を足すだけなので、local-first とも整合する。ただし下記の
> 不変条件（§5）を外すと「自動生成＋高頻度レビュー」の破綻（[00](00-overview.md) 方針・
> ユーザー CLAUDE.md）に落ちるため、pull型・決定論・原本非複製を厳守する。

### 原本の所在（重要）

- **権威データ（source of truth）は OpenProject / devlog 等にある**。朝凪はそれを複製・上書きしない。
- 朝凪の可視化は「**今メールで動いていること**」の俯瞰であり、タスク管理ツールの置き換えではない。
- 各案件からは既存の連携リンク（`opUrl` / `openproject-links.json`・[07](07-integrations.md)）で
  権威データへリンクアウトする。

---

## 1. 用語 — 「誰待ち（だれまち）」

案件が「誰の行動待ちで止まっているか」を表す概念の呼び名。

- 採用: **誰待ち（だれまち）**。「今ボールを持っているのは誰か（whose court the ball is in）」という
  ビジネスで一般的な「ボールの所在」メタファの、短く直感的な日本語。
- 不採用: ~~泊まり先~~（初稿の仮称。「泊まる＝宿泊」の語感で、案件が止まっている/保留の意味に
  ならず、業務語として通じない）。
- UI のラベルは2状態で言い切る:
  - **相手待ち**（自分が最後に送った＝ボールは相手）… 例: 「相手待ち 3日」
  - **自分待ち（要返信）**（相手が最後に送った＝ボールは自分）
- 止まっている長さは **滞留日数**（最後の動きからの経過日数）と呼ぶ。

---

## 2. データ源（既存の何に乗るか）

すべて朝凪が既に持っている/導出しているもの。新しい収集はしない。

| 可視化 | 既存の材料 |
|---|---|
| 案件そのもの | `ProjectHub` / `Project`（AI抽出・pull型・[route](../src/app/api/projects/route.ts)）= name / parties / status(進行中・要確認・完了) / statusLabel / pct / next / due / **anchorId**（最新メール） |
| 誰待ち | `anchorId` から辿るスレッドの**最終メールの方向**（自分が送ったか相手か）＋**経過日数**。自分の判定は接続済みアカウントのアドレス（`listAccounts`）/ 送信箱 / `Email.replied` |
| 関係者 | `Project.parties`（org＋person）＋スレッド参加者（from/to/cc）＋`ContactMeta`（company・VIP等の端末内メタ・[04/連絡先]）＋`AiSummary.participants`（[thread-digest]） |
| 権威リンク | `openproject-links.json` / `opUrl`（[07](07-integrations.md)） |

## 3. 3つのビュー（価値/コスト順に段階導入）

フルの「ワークフロー可視化ツール」を一気に作らず、小さく確実に。すべて **ProjectsView への追加
または案件詳細**として収め、別アプリ化はしない。

### (A) 誰待ちチップ
各案件（と、できればスレッド本文ヘッダ）に「**相手待ち N日 / 自分待ち（要返信）**」を表示。
- **決定論**で算出（§4）。新データ不要・一番小さく一番効く。まずここで価値を確かめる。

### (B) 関係者マップ（ミニ構成図）
案件ごとにインライン SVG で「**自分 → org → 担当者**」のノード図。
- `Project.parties`＋スレッド参加者＋`ContactMeta` から導出（決定論）。
- 図はあくまで「このメール群から見えている関係者」。実在する組織図を創作しない（§5）。

### (C) プロジェクト・ボード
案件を status 列（**進行中 / 要確認 / 完了**）に並べる読み取り専用カンバン。
- 既存 `ProjectHub` をそのまま再利用。並べ替え・ドラッグでの状態変更はしない（原本非複製）。

---

## 4. 「誰待ち」判定ロジック（決定論・LLM を使わない）

**必ず決定論**で出す。LLM 判定にすると毎回ブレて、俯瞰ビューの信用を損なう。

入力: 案件の `anchorId` が指す**最新メール**（または最新スレッド）。
1. その最新メールが **自分の送信**（送信箱 / from が自分のアカウントアドレス）か **相手からの受信**かを判定。
2. 経過日数 = 今 − 最新メールの日時。
3. 出力:
   - 最新が**自分の送信** → **相手待ち**（滞留日数 = 経過日数）。
   - 最新が**相手からの受信** かつ 未返信（`replied` でない） → **自分待ち（要返信）**。
   - 最新が受信だが返信済み（かつその後音沙汰なし）→ **相手待ち**。
4. しきい値（例: 相手待ち7日以上を「停滞」として色を強める）は UI 側の軽い既定値。判定自体は上記のみ。

> 補足: 自分のアドレス集合は `listAccounts()`（Gmail/IMAP の接続アカウント）から得る。
> 送信/受信の別は、キャッシュ上の `state`（sent 等）・`from` 一致・`replied` フラグで決める。

---

## 5. 不変条件（壊してはいけない）

- **pull型を死守**: 開いた時＋更新ボタンで再生成・再計算する。日次スナップショット保存や
  常駐スケジューラは作らない（[00](00-overview.md) 方針・「自動生成＋高頻度レビューは破綻する」）。
- **誰待ちは決定論**（§4）。LLM で推測しない。
- **local-first**: 関係者グラフはヘッダ＋`ContactMeta`（端末内）から描く。図やデータをどこにも送らない。
- **偽機能禁止**: ノード/エッジ/チップは実メール・実案件から導出したものだけ。ダミーの組織図や
  架空の進捗を描かない。
- **原本を複製・上書きしない**: 権威は OpenProject 等。朝凪は俯瞰＋リンクアウトに徹する
  （ボードでのドラッグ状態変更など、原本を書き換える操作は入れない）。

---

## 6. 実装フェーズ（提案）

1. **Phase A**: 誰待ちチップ（決定論・新データ不要）。ProjectsView のカード＋（任意で）本文ヘッダ。
2. **Phase B**: 関係者マップ（インライン SVG・`parties`＋参加者＋`ContactMeta`）。
3. **Phase C**: プロジェクト・ボード（status 列の読み取り専用カンバン）。

各フェーズは独立 PR。既存の [ProjectsView](../src/components/mail/ProjectsView.tsx) への追加を基本とし、
AI 生成経路（`/api/projects`）には触れない（誰待ち・グラフは生成済みハブ＋キャッシュから導出）。
